D1 · Distributed Data Contract Debug

四个 Worker 各自都对，为什么合起来会崩？

100-step GRPO 实验完成第 10 步后，在下一批 rollout 合并时失败。这份记录从 DataProto.concat 的断言出发，追到 worker 局部推断 reward schema 的设计缺陷，并用确定性回归测试与真实一步训练验证修复。

日期 2026-08-01 框架 Agent-R1 + veRL 任务 HotpotQA 状态 根因确认 · Unit + E2E 通过

01 · 一句话结论

每个 AgentFlow worker 只根据自己分到的轨迹推断 reward_extra_keys。有 final answer 的 worker 得到 [em, format_valid, token_f1]，整块都没有 reward payload 的 worker 可能得到空列表；DataProto.concat 要求所有 worker 的 metadata 完全一致，因此在合批时触发断言。

这不是 D0 的重复修复 D0 处理的是“合批成功后，轨迹级 format_valid=None 如何解释”；D1 处理的是“合批之前，各 worker 连有哪些字段都不一致”。两个故障位于流水线的不同边界。

02 · 故障发生在哪

正式运行 hotpotqa_grpo_hybrid_format_20260801_173806 使用 4 张 GPU、4 个 prompt、每个 prompt 采样 n=4。训练完成第 10 个 optimizer step；生成第 11 批轨迹时，在 manager 收回四个 worker 输出后崩溃：

output = DataProto.concat(outputs)

assert merged_meta_info[k] == v,
    f"Conflicting values for meta_info key '{k}'"

AssertionError: Conflicting values for meta_info key 'reward_extra_keys'

这条堆栈提供了三个强约束：reward 已在各 worker 内算完；错误发生在 rollout 合批；尚未进入第 11 步的 advantage、loss 或 backward。因此学习率、显存、GRPO 公式和 W&B 都不是这次异常的根因。

03 · 定位过程：从断言追到生产者

排查从 DataProto.concat 消费的 metadata 反向追踪，而不是先改断言。

步骤观察推断或排除
1. 锁定失败键断言明确指出 reward_extra_keys不是 tensor shape，也不是普通 metrics；只需追这个 metadata 的生产路径
2. 阅读 worker 后处理每个 worker 对自己的 reward_extra_info 做集合并集schema 是 data-dependent，而且只在局部 chunk 内决定
3. 构造最小反例worker A 有三项 reward；worker B 的本地轨迹全为空 payloadA 的键列表为三项，B 为零项，二者都符合各自局部数据
4. 阅读 concat 契约veRL 对非 metrics metadata 执行相等断言跨 worker schema 未对齐时必然失败；断言本身在正确保护数据契约
5. 用真实 concat 复现测试输入使用两个 DataProto，不 mock concat复现了原故障路径，而不是只测试 helper 的返回列表

完整数据流被压缩为：

worker A local chunk
  -> reward_extra_keys = ["em", "format_valid", "token_f1"]

worker B local chunk
  -> reward_extra_keys = []

ray.get([A, B, ...])
  -> DataProto.concat(outputs)
  -> metadata equality assertion
  -> crash before step 11 update

04 · 根因：结构 Schema 与数值语义是两层契约

原实现把 reward_extra_keys 定义为“本 worker 实际见过的字段”，但 manager 把它当作“整个 batch 的公共 schema”。局部观察被误当成全局契约，才是根因。

分布式合批前，所有 shard 必须先共享相同的字段集合；某个 shard 没有值，不等于整个 batch 没有这个字段。

这里要区分两个问题。D1 的结构层只负责让每个 worker 都拥有相同的列，缺失位置暂时填 None；D0 的语义层才负责在 trajectory aggregation 时判断，例如没有 final answer 的 format_valid 应映射为 0.0。如果 D1 就把所有缺失值一律填零，会把未知的未来 reward component 也悄悄定义成零，反而掩盖错误。

05 · 修复前后代码差异

修复前：四个 worker 返回后立即 concat，默认它们的 schema 天然一致。

outputs = ray.get(output_refs)
output = DataProto.concat(outputs)

修复后：manager 先取所有 worker 字段的全局并集，再为缺列的 shard 补等长 object array，并统一 metadata。

def _align_reward_extra_schema(outputs):
    worker_keys = [
        list(output.meta_info.get("reward_extra_keys", []))
        for output in outputs
    ]
    merged_keys = sorted({
        key for keys in worker_keys for key in keys
    })

    for output in outputs:
        for key in merged_keys:
            if key not in output.non_tensor_batch:
                output.non_tensor_batch[key] = np.full(
                    len(output), None, dtype=object
                )
        output.meta_info["reward_extra_keys"] = merged_keys

    return merged_keys

outputs = ray.get(output_refs)
_align_reward_extra_schema(outputs)
output = DataProto.concat(outputs)

补丁位于 agent_r1/agent_flow/agent_flow.py 的 manager 合批边界，保留了 DataProto.concat 的严格断言。

  1. schema 来源正确：公共字段由全体 worker 的并集决定，不再由任一局部 chunk 决定。
  2. 行数保持一致：缺失列按该 worker 输出长度补齐，concat 后列与样本严格对齐。
  3. 职责没有混淆：D1 只修结构，具体 reward 缺失值的业务语义继续由下游显式处理。
  4. 断言继续有效：其他 metadata 冲突仍会被 veRL 立即暴露。

07 · 工程结论与事实边界

  1. 分布式 shard 不能各自定义公共 schema。局部数据只负责值，全局 manager 负责合并后的字段契约。
  2. 不要删除有价值的断言。断言暴露了真实的数据不一致；绕过它只会让列错位或静默污染进入训练。
  3. 结构缺失与业务零分不同。None 是“此 shard 没提供值”，0.0 是 reward 的具体语义，两者必须分层处理。
  4. 随机 E2E 不能替代确定性反例。一个 smoke 跑通可能只是没抽中故障形态，所以需要直接构造冲突 schema 的回归测试。
  5. 本次没有恢复原 100-step 实验。当前证据只支持“原 concat 根因被覆盖，完整一步训练未回归”；长期稳定性与性能收益仍需后续正式运行验证。

08 · 面试中如何讲这次 Debug

我的 HotpotQA GRPO 实验跑到第 10 步后，在下一批 rollout 的 DataProto.concat 崩溃，断言指出 reward_extra_keys 冲突。我沿 metadata 生产路径发现，每个 AgentFlow worker 都根据本地 chunk 独立推断 reward 字段：有 final answer 的 shard 会看到 EM、F1 和格式分，没有 reward payload 的 shard 则可能得到空 schema。两边局部都合法，但不满足分布式合批契约。我没有删除 veRL 的断言，而是在 manager 边界计算全局字段并集，为缺列 shard 补等长 None 数组，再统一 metadata。随后用真实 DataProto.concat 构造确定性反例，两个单测通过，并跑通 4 GPU、16 条轨迹的一步 GRPO 闭环。

事实边界 这次实验验证的是跨 worker reward schema 契约和训练闭环恢复；它不证明模型效果提升，也不等于原 100-step 实验已经续跑完成。
