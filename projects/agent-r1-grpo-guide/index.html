实际执行链

从 shell wrapper 到 EM reward 的真实调用关系。两份 shell 文件看起来差异很大，是因为它们处在不同层，而不是实现了两种 GRPO。

1. short wrapper检查路径、激活 conda、设置本机模型和数据路径。
2. 官方 run_grpo.sh计算 batch，拼 Hydra 参数，选择 GRPO。
3. main_agent_ppo创建 Ray/FSDP actor、vLLM rollout 与训练循环。
4. HotpotQA AgentFlow多轮生成工具调用，FAISS+BGE 返回 Wikipedia passage。
5. normalized EM提取最后一个 answer 标签并与 GT 标准化精确匹配。
6. GRPO update同题 4 条 rollout 组内比较，计算 advantage 并更新 actor。

为什么有这么多不同

原版面向较完整的 4-GPU 长实验；short 版面向当前机器的“先证明流水线真的能更新”实验。

配置覆盖优先级

从左到右优先级升高。同一个键出现多次时，最终传给 Hydra 的后一个值生效。

1YAML 默认值

agent_r1/config/agent_ppo_trainer.yaml 和 recipe 配置。

2原版 shell 默认值

例如 rollout n=8、显存利用率 0.7。

3short 环境变量

原版脚本用 ${VAR:-default} 读取这些值。

4short CLI 覆盖

借助原版末尾 "$@"，最终覆盖同名 Hydra 参数。

容易忽略的例子：LOG_PROB_BUDGET=8 和 n=4 会让原版先算出 log-prob micro batch 为 2，但 short 第 90 行又显式传入 ...=1，所以最终生效值是 1。

动手改参数时先检查

1. group 必须有比较空间

n=1 时无法形成真正的组内相对优势；GRPO 实验至少使用 2，通常使用 4 或 8。

2. rollout budget 必须能整除 n

脚本使用 bash 整数除法。比如 18/4 会直接变成 4，实际只使用 16 条 rollout 的结构。

3. 同组 reward 全相同

如果同题 4 条结果全为 0 或全为 1，组内 advantage 缺少差异，该题这一组提供的策略梯度会很弱或为零。

4. 20 条集不是效果结论

它适合验证训练链路和观察单题轨迹；正式 baseline 需要固定、更大的 held-out validation split。

5. EM 是当前优化目标

模型语义正确但表达不等于 GT 时仍可能拿 0。训练前应记录 GT 错标和别名覆盖风险。

6. 先看 step 0

val_before_train=True 给出基线；否则只看到训练后结果，无法判断 10 steps 到底提升还是退化。
